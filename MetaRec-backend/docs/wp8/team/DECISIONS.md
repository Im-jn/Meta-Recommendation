# WP8 Shared Decisions (Member A ↔ Member B)

Contract questions both members must agree on before D2 code depends on them,
plus the hand-offs each side is waiting for. Proposals marked **Proposed (A)**
are already implemented on the Member A branch so there is something concrete
to review; changing one means changing the model, the schema and the tests
together, which is fine — say so here first.

**How to use:** reply in the *B's answer* column (or in a PR comment), then
set the status to **Agreed** or **Changed**. Once every row is Agreed, the D1
contract is frozen.

Where things live:
- Event model and rules: [`langgraph_metarec/wp8_trace/models.py`](../../../langgraph_metarec/wp8_trace/models.py)

## Rules to agree

| # | Question | Proposal | Why | Affects | Status | B's answer |
|---|---|---|---|---|---|---|
| R1 | How is a cancelled run recorded? | One `error` event on the cancelled run's own `run_id`, with `status: "cancelled"` and `error.error_class: "CancelledError"`. No `*_end` follows. | D0: LangGraph reports cancellation and timeout as `chain_error(CancelledError)` (E9, E10). The brief says a terminal error reuses the lifecycle's `run_id`. | Store status derivation, drawer, diff severity (`cancelled` vs `error`) | Proposed (A) | |
| R2 | How is a failed run recorded? | One `error` event with `status: "error"` on the failed run's `run_id`; ancestors that catch the exception still end normally (E7). | Same mechanism as R1; matches the D0 data. | Store, drawer, nested error counts | Proposed (A) | |
| R3 | Where may `state_diff` appear? | Only on `node_end`. A failed or cancelled node has no diff. | The diff compares a node's input with its *returned* update, which exists only when the node returns. | B's differ and drawer | Proposed (A) | |
| R4 | Where may adapter metadata appear? | `llm_attempt` only on `llm_attempt_adapter` events; `tool_scope` only on `tool_scope_adapter`; `tool_health` only on `tool` or `tool_scope_adapter`. | The brief says where each "occurs"; making it a hard rule stops misplaced data. WP5/WP7 should agree too. | Adapter sink, drawer | Proposed (A) | |
| R5 | Status of start and end events | Starts are always `running` with `duration_ms: null`; ends are never `running`. An unknown parent does **not** change an event's status; it is handled by R12. | Implied by the brief, not stated. Event status describes the lifecycle; trace completeness is a trace-level fact. | Store, timeline | Proposed (A) | |
| R6 | Instance implies definition | Any event with a `graph_instance_id` also carries its `graph_definition_id`. | The DAG and diff need the definition for every node event. Implied, not stated. | Store, DAG, diff | Proposed (A) | |
| R7 | Who assigns `sequence` and `event_id`? | The collector emits drafts with timing (`timestamp_utc`, `monotonic_offset_ms`); the **sink** assigns `sequence` and `event_id` atomically at append. | Sequence must be allocated in one critical section with the append (brief §Atomic store); only the store can do that. | `TraceEventSink` interface | Proposed (A) | |
| R8 | Trace status for each outcome | Uncaught failure → `failed`; any cancelled run (task cancel, request timeout) → `cancelled`; crash with open runs → `incomplete`; caught nested failure → `completed` with `summary.error_count > 0`; truncation does not change status (it sets `truncated: true`); a trace that would otherwise be `completed` but has an orphan (R12) or an untraced graph (R15) → `incomplete`. No status is final before the R11 finish condition holds. | The golden manifests record these as `expected_trace_status`. The caught-failure case (E7) is the judgement call: the run did complete, but the error must stay visible. | Store finalisation, status banner, diff | Proposed (A) | |
| R9 | What does "nesting depth 6" count? | A safe value contains at most 6 levels of lists/objects; level-7 containers are rejected. | Needed so B's redaction bounds and the model agree on the same boundary. | Redaction bounds | Proposed (A) | |
| R10 | Draft error codes | `cancelled` and `execution_failed`, with generic safe messages. | Placeholders in the golden lists; B owns the reviewed code list and messages. | Redaction, drawer | Proposed (A), B to replace | |
| R11 | What is one trace, and when is it finished? | **One debug run = one trace.** The behaviour test calls `handle_user_request_async` up to twice (query turn, then auto-confirm turn), so a trace has **one root per service turn**: each a `request-orchestrator@v1` graph with `parent_run_id: null`, in turn order. The turns are siblings; no parent link is invented between them. Every other graph instance descends from a turn root. The brief's "one root" check is read as "one root per turn, and no other parentless graph". **Finish condition:** the trace leaves `running` only when the route has sealed it (H7) **and** every lifecycle has closed; a root's `graph_end` alone never finishes it, because the next turn or the background task may still be running. If the process dies first, recovery marks it `incomplete` (B). | `run_behavior_create` makes two service calls (`internal/debug/router.py`), and the trace API is keyed by the debug run. The task graph outlives the turn-2 root (E3). Golden case `full_debug_run` freezes this shape. | Collector status derivation (M6), store finalisation, DAG root grouping, diff | Proposed (A) | |
| R12 | A lifecycle whose parent is unknown | An **orphan** is a graph, node or child span whose observed `parent_run_id` never started in this trace, or a parentless graph that is not a turn root (R11: a parentless graph is a turn root only if it is `request-orchestrator@v1` and the trace is not sealed). The collector stores **no event for an orphan or anything under it** — no reparenting, no guessed parent, no event with a dangling parent — and counts every withheld event in `dropped_event_count`. The trace then finishes `incomplete` (R8). Event-level `incomplete` appears only on the `trace_truncated` marker; a crash's unmatched starts stay unmatched and the UI shows them as incomplete once the trace is terminal. | The brief allows "incomplete or drop with accounting" and forbids reparenting. Withholding keeps every stored parent reference valid (an acceptance row) and keeps R5 simple, while the trace status and dropped count say honestly that part of the path is missing. With correct propagation (R13) there are no orphans, so fidelity fixtures still show zero lost events. | Collector (M5), store, status banner | Proposed (A) | |
| R13 | What does Invariant 2 ("explicit propagation") require? | (1) `TraceContext` is an explicit argument at every service and runner call site from the debug route down (H6, M4); nothing looks it up from a global or contextvar. (2) Every graph call goes through `invoke_with_wp8_trace` (R14 enforces it). (3) Within one asyncio task, the callback *parent* comes from LangChain's runnable context, which LangGraph sets for every node; the helper never passes `metadata` or `configurable`, because LangChain replaces explicit keys wholesale and would drop the parent and checkpoint namespace. (4) At any boundary that does not copy context (the background-task hand-off today; a queue, thread pool or resumed task later) the caller passes `trace_ctx.handoff(parent_run_id)` with the run id read at the call site, and the helper applies it whatever callbacks the call already carries (M6). (5) A missed boundary becomes an orphan (R12) and an `incomplete` trace, never a silent new root. | The brief requires parentage from the callback `run_id`/`parent_run_id` chain and says implicit task-local context *alone* is not enough. Here identity and the collector travel explicitly, the chain supplies only the parent inside a task, and every place the chain can break is either explicit (hand-off) or detected (orphan). Considered instead: give the nodes that call nested graphs a `config` parameter and pass it on. It passes the same values the context already holds, changes node signatures in three graphs, and checks nothing that R12 and R14 do not. | Helper, runner plumbing, M6 hand-off, viva | Proposed (A) | |
| R14 | What does the guard test check? | `tests/test_wp8_integration.py` parses every production module (`MetaRec-backend/**/*.py` except `tests/`, `scripts/`, `alembic/`, `.venv/`) with `ast` and fails on any **attribute** named `ainvoke`, `invoke`, `astream`, `stream`, `astream_events`, `astream_log`, `abatch` or `batch` outside `wp8_trace/invocation.py` — attribute, not call, so `run = graph.ainvoke` is caught too. Non-graph objects that need one of these names go on an explicit allowlist with a reason (empty today: the five runners are the only uses). It also checks each of the five registered `graph_definition_id`s is passed to the helper at exactly one production call site, and a planted-bypass test feeds the scanner `await graph.ainvoke(x)`, `graph.astream(x)` and an aliased call and expects all three flagged. | Covers both invariants it exists for: no graph call outside the reviewed path (2) and no streaming pass beside `ainvoke` (1). A text search misses aliases and matches comments. | M4 | Proposed (A) | |
| R15 | What if a graph cannot be traced? | Tracing never fails or repeats the business call. If the helper is given an unregistered `graph_definition_id`, or a graph whose structure no longer matches its registered topology, it runs `graph.ainvoke` **once, untraced** (the runner's plain call), logs a warning, and tells the collector through `on_untraced_graph(graph_definition_id, reason)` so the trace finishes `incomplete` (R8). Callbacks inherited from a traced parent may still arrive for that graph under LangGraph's default name `"LangGraph"`; the collector treats them as an unknown definition and withholds them (R12). Drift is meant to be caught earlier, by the topology snapshot test in CI. | Raising would fail a real recommendation only because tracing was on, and the business code would run zero times instead of once (Invariants 1 and 3). | Helper (M3), collector (M5), status | Proposed (A) | |
